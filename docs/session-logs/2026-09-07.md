## What happened

**T = 37, and it had been 37 since 2026-08-17.**

The task was to take the one measurement step 3 still listed as outstanding. The measurement
was already in the repository. What was outstanding was a comment.

## The measurement

`tests/fixtures/timing/timer-only.asm` was built for exactly this: the timed region contains
no WSYNCs, so nothing competes with the timer, and the frame length is `225 + T` by
construction. T reads straight off Stella's frame-stats overlay with no debugger scripting —
the fixture's author arranged for the answer to appear in the one number a screenshot can
capture.

| | Scanlines | T |
|---|---|---|
| Our emulator, five consecutive frames | 262 | **37** |
| Stella 7.0c, three launches at 4s, 15s and 25s settle | 262 | **37** |

Steady, not a lucky frame — the three Stella launches were separate processes, and
`docs/running-in-stella.md` warns that an inconsistent count flickers between 261 and 263.

The ROM was assembled with **DASM** rather than our assembler, so Stella and our emulator were
not running bytes from a common source. They turned out to be identical bytes anyway, which
the probe asserted before trusting the comparison.

## The finding: a stale comment outranked the code for three weeks

`packages/emulator/test/timing-fixtures.test.ts` said:

> *PENDING a Stella reading. This emulator currently gives T = 38 for TIM64T #44.*

Both sentences were false when I read them. Commit `be3fd27`, **2026-08-17**, is titled
*"Correct 6532 timer write semantics; emulator now matches Stella"* and its message records
the reading: `timer-only` measured 262 on Stella against 263 predicted, T = 37 where starting
the divider at zero gave 38. `riot.ts:85` carries the same measurement in a comment beginning
**MEASURED, not assumed**. `docs/session-logs/2026-08-17.md` has it in a table.

The test's comment was never updated. Four documents then cited **the comment** rather than
the code:

| Where | What it said |
|---|---|
| `packages/runtime/src/frame.ts` | "still marked PENDING a Stella reading in `timing-fixtures.test.ts`" |
| `docs/kernel-measurements.md` | "The 6532 timer's T. `timing-fixtures.test.ts` still marks it PENDING" |
| the step-3 design spec | "`TIM64T`'s T is still marked PENDING in `timing-fixtures.test.ts`" |
| `docs/session-logs/2026-08-29.md` | "the timer's T is still PENDING a Stella reading" |

Every one of them attributed the claim honestly and correctly. The thing they cited was
stale.

### Why no test caught it

The assertion was a range:

```ts
expect(t).toBeGreaterThan(30);
expect(t).toBeLessThan(45);
```

**30 < T < 45 cannot tell 37 from 38.** The model changed underneath it and the test went on
passing, so nothing forced anyone back to the comment. The range was chosen deliberately, and
the reasoning written above it was sound at the time:

> *The expected value is deliberately not asserted yet rather than being pinned to this
> emulator's own output, which would make the test tautological.*

That is correct while a reading is outstanding — and it **inverts** the moment the reading
arrives, because 37 is then Stella's number and pinning it is what makes the test
non-tautological. The comment that justified the loose assertion is the same comment that
should have been deleted, so the argument for keeping it protected itself.

The assertion is now `expect(first.scanlines - 225).toBe(37)`.

### The class of defect

The same shape as the previous session's `SWCHA` emitted as `$0282`: something that compiled,
ran, passed, and told a lie nothing checked. The difference is where the lie lived — not in
emitted code but in prose *about* the code, which no test can execute.

The general lesson is narrow and worth stating: **a measured value belongs in an assertion,
not in a comment.** A comment claiming a measurement is pending cannot go red when the
measurement lands. Where a value is genuinely un-measurable in CI, the assertion should at
least be tight enough that the value moving breaks it.

Worth noting what did work: `riot.ts`'s comment was accurate the whole time, because it was
written in the commit that made the measurement. Distance from the measurement is what
correlated with staleness.

## What was NOT changed, deliberately

**The frame driver still counts WSYNCs.** T being measured makes `TIM64T` *available*, not
*required*, and switching the frame driver is language-widening work with no requirement
forcing it.

The reason for counting WSYNCs never depended on T being unmeasured — that was one of two
reasons `frame.ts` gave, and the other one stands on its own: the reference kernel's own two
timer constants were **both** off by one until a measurement corrected them, so a
timer-bounded region hides an off-by-one that a counted region cannot. `frame.ts`'s comment
now says that, instead of citing a pending measurement.
