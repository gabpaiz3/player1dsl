# Session log — 2026-08-30

**Branch:** `step3-plan4-rule-lowering`
**Scope:** increment 5c — a TIA that tracks objects and latches collisions, built because
plan 4's own `rules-behaviour.test.ts` could not be written against a machine that reported
none.

## What happened

`packages/emulator` now tracks all six TIA objects at colour-clock resolution and serves real
values from all eight collision registers. Along the way it found **three defects, two of
them in code that had been passing tests for weeks**, and one measurement that contradicted
the model and was settled by Stella.

292 tests, `npm run check` green, CI green on every push.

## The three defects

### 1. Every TIA write was applied one instruction early

`Machine.runFrame` ran `cpu.step()` to completion and only then ticked the TIA, so `onWrite`
observed the beam at instruction *start*. A 6502 writes on its final cycle.

Measured: three `sta COLUBK` after a WSYNC recorded at clocks 0, 9, 18 where the hardware
writes at 6, 15, 24.

The regenerated golden is the proof it was a uniform correction: **990 of 6990 records moved
and zero changed line, register or value.** The shifts were 6 (270 records) and 9 (720), each
exactly its addressing mode's address-work cost. `frame-timing` and `kernel-fixtures` assert
absolute scanline counts and did not move, which is what says the correction did not eat a
boundary.

### 2. `PosObjectX` applied every object's fine adjustment except the last one twice

The routine ends `sta WSYNC / sta HMOVE / rts` and is called once per object with **no
`HMCLR` between calls**. One `HMOVE` strobe moves every object whose `HMxx` is set, so the
second call's strobe re-applied the first object's adjustment.

`tank0` authored at x = 70 rendered at 74.

Fixed in **both** copies — `emit.ts`, which the compiler emits, and the reference kernel it
was copied from. Fixing only the compiler would have made the two ROMs disagree about
positioning, and the reference is what the golden harness compares against.

The `HMCLR` sits *before* the routine's first WSYNC. Every cycle after that WSYNC moves the
beam the divide loop counts against, so an instruction added there would shift every object
nine pixels right; before it, the WSYNC absorbs the cost. Confirmed: `HMP0`/`RESP0`/`HMP1`/
`RESP1` land on pixels 49/61/79/91 in both ROMs, exactly as before the fix.

### 3. An authored x does not render on screen pixel x

`bounds.ts` assumed it did and said so under "Not measured". It renders at **x + 3**.

## What Stella showed, and why it was load-bearing this time

Three fixture pairs, each answering with a **whole-screen colour** rather than a sprite
position. That choice was made after abandoning an attempt to measure placement off a
screenshot: locating the emulator's window reliably enough to calibrate against turned out to
be a screen-scraping problem, and a measurement whose error bars come from window management
is not a measurement. One attempt photographed an unrelated browser window.

| fixture | our model | Stella | verdict |
|---|---|---|---|
| `double-hmove` | red, P0 displaced | **red**, one *merged* bar | model right |
| `double-hmove-cleared` (control) | black | **black**, two separate bars | control fires |
| `collide-playfield`, x = 0 | red | **red** | — |
| `collide-playfield`, x = 1, 2, 3 | red | **black** | **model wrong by 3** |

The first pair confirmed the double-HMOVE and its control proved the fixture could report the
other answer. The second **contradicted the model**, and the design had already committed to
what happens then: *"these values are the documented starting point and lose to any
measurement that disagrees."* `PLAYER_STROBE_DELAY` went from 5 to 8.

**Why the second fixture had to exist.** `double-hmove` collides P0 against P1, both placed by
the same routine, so a uniformly wrong delay moves both and the flip lands in the same place —
Stella would have agreed with a wrong model. `collide-playfield` collides P0 against the
playfield, whose position the beam fixes and no strobe places. Only that one is absolute.

## Decisions made

| Decision | Rationale |
|---|---|
| All six objects, not just P0/P1 | Missiles and the ball are *cheaper* than players — an enable bit and a width, no graphics byte — so stopping at players would have left 13 of 15 latch bits still returning a lie for a small saving. |
| Presence mask, not colour | Collisions need PRESENCE. `objects.ts` answers "which objects cover this pixel"; a framebuffer is "and what colour", a second query over the same state. The seam is left deliberately rather than discovered later. |
| A per-line mask rather than interval intersection | Intervals are faster and cannot express a mid-line `GRP0` rewrite, which is what a kernel *is*. The mask costs under four million byte writes to regenerate the whole 90-frame golden. |
| The write-timing fix landed **alone** | So that every changed clock in the regenerated golden had exactly one possible cause. |
| An enabling `VDEL` write **throws** | Vertical delay draws the graphics byte written a line earlier. Ignoring it would draw the wrong row and latch a collision that never happened. `cycleCost`'s refusal to guess is the model. |
| `HMCLR` exempted from the vertical-blank pixel comparison | It is a strobe whose position carries no meaning, and sitting before the anchoring WSYNC it inherits the caller's phase. Every other record is still compared on its exact beam clock. |

## Findings that contradicted a prediction

### The tanks touch, and the design said they could not

The design's correction of 2026-08-29 derived geometrically that *"the two sprites miss
contact by about a pixel on line 139, so `CXPPMM` never sets"*, and concluded that collision
and the `hitFlag` debounce were "covered nowhere at all".

Measured against a machine that can see a collision: contact at frame 35, `score0` 3 → 4,
`hitFlag` latching and clearing at frame 50. **The score increments exactly once across 15
frames of contact.** The debounce works, and it always did — nothing could see it.

The correction's arithmetic was fine. Its premise — that an authored x is where the object
lands — was not, twice over.

### `emit.ts` was right and the emulator was wrong

Increment 5b justifies hoisting the field's colour writes with *"the reference reaches COLUP1
on the first visible line at colour clock 66"*, derived by hand. The emulator had been saying
**60**, and nobody noticed the disagreement. Corrected, it says 66. The hoist argument
survives, and stops resting on a hand-derivation the model contradicted.

The prediction written before the recomputation said the corrected number would land *later
than* 66 and strengthen the case. Right in direction, wrong in letter: it landed *on* it.

### The golden did not move when the offset was corrected

Predicted before regenerating: a uniform offset shifts both tanks equally, so contact is
unaffected, and the script never brings a tank near a wall. Confirmed —
`tests/goldens/tank-arena.trace` is byte-identical across the `PLAYER_STROBE_DELAY` change.

## Still unmeasured, carried forward

- **Whether the three pixels belong to the strobe or to the HMOVE.** The sweep measures them
  as one composite because `PosObjectX` always does both. Separating them needs a fixture
  that strobes `RESPx` and never strobes `HMOVE`.
- **`MISSILE_STROBE_DELAY`, `PLAYER_HBLANK_POSITION`, `MISSILE_HBLANK_POSITION`.** Shifted by
  the same three on the assumption that the mechanism is shared. Labelled UNMEASURED in
  `objects.ts`.
- **Vertical delay.** Not modelled; an enabling write throws.
- **Colour.** Presence is not colour. A wrong playfield bit order, wrong REF mirroring or a
  sprite one column off *in the picture* still needs Stella and a human eye. The framebuffer
  seam is where it would attach.
- **`DEFAULT_STACK_RESERVED`.** Still 16, still a guess.
- **`dasmRom` in `packages/emulator/test/support/roms.ts`** still reads the pre-split
  `build/<name>.bin`. Nothing calls it, so nothing is wrong today.

## What this unblocks

Increment 6's `when A hits B` lowering and the `hitFlag` debounce now have a verification
path, which is the whole reason 5c was inserted before them. Plan 4's Task 8 — the input
script that has to drive the tanks into real contact — also becomes checkable: "did they
touch" is now a question the emulator answers rather than a geometric derivation, and the
committed script already makes contact.
