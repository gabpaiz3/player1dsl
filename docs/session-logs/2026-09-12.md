## The single mistake underneath three of them

**Pairing by array index.** `bindObjects` binds a band's scores before its actors, so an index
into that list means "the nth holder of this band" — and every site indexed it with an actor's
or a score's position in its *own* list. The two coincide exactly when a band holds only one
kind of holder, which is every band in the one example that existed.

The fix is one helper, `objectFor(bindings, holder)`, which looks the binding up **by name**
and throws when there is none. Three call sites collapse into it, and `?? 'p0'` — which drew
two holders with one object — is gone from all of them.

Positioning had the same shape in a different place: vertical-blank setup positioned the first
band's objects at the first band's *scores'* x, `firstScores[i]?.x ?? 0`. It now asks the
holder itself, whether that holder is a score or an actor.

## The band-transition rule was wrong, not just its inputs

`layout` charged a transition only for objects the **previous** band had placed:

> *A boundary costs scanlines only for objects that were already placed somewhere else.*

An object drawn by band N and by no band before it is not free — it is **unplaced**. That is
how P1 ended up at pixel 120 in the one-score scene: it belonged to the field, to no band
before it, and to neither the first band's vertical-blank positioning nor the transition.

Every object a band draws is now placed at its boundary, the first band excepted because
vertical blank places everything there. For `tank-arena` the two rules agree — both bands use
both objects — which is why the ledger is byte-identical and the 90-frame comparison never
moved.

## `within` means something now

It was parsed, checked for existence (E206), passed into lowering, and used **in a comment**.
The bounds came from whichever ledger row carried the note string `'the open field'`.

**E219**: an actor may only be bounded by the band it lives in. A band is a horizontal strip
drawn by its own kernel and an actor is drawn by the kernel of its own band, so clamping tank0
to the HUD's scanlines would confine it to lines nothing draws it on. There is no sensible
picture to emit, so the compiler refuses rather than choosing one.

That also retires the note-string lookup: bounds now come from the ledger row whose **band**
is the actor's, and whose kind is `loop`. A human-readable note is not a key.

## Two more of the same class, found by reading

- **E507, more than one playfield.** `COLUPF` is written once in one-time setup from
  `scene.playfields[0]`, while layout already gives each band its own playfield and decomposes
  them independently. A second one in another colour would draw in the first one's. Refused
  rather than fixed: rendering it properly needs a per-band COLUPF write whose line cost
  nothing has measured, and inventing that cost is the assumed zero the ledger exists to
  prevent.
- **`CTRLPF_MODE` is keyed by the IR's own union** instead of `string`, so the lookup is total
  and the `?? 0` is gone. It mattered: 0 is `repeat`, so a mode the table forgot would have
  rendered un-mirrored rather than failed.

## What did not change

The ledger for `tank-arena` is identical row for row, and the 90-frame golden comparison is
still at zero mismatches. Every fix above is reachable only by a scene the example does not
contain — which is the point, and also the only reason to trust that the example still works.

## Still open from the review

- **The ball and missile strobe delays**, both UNMEASURED, with `strobe()` using the missile's
  for the ball.
- **Coordinate semantics**: an actor's `y` is the field loop's counter and `x` renders at
