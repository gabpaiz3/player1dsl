## The single mistake underneath three of them

**Pairing by array index.** `bindObjects` binds a band's scores before its actors, so an index
into that list means "the nth holder of this band" — and every site indexed it with an actor's
or a score's position in its *own* list. The two coincide exactly when a band holds only one
kind of holder, which is every band in the one example that existed.

The fix is one helper, `objectFor(bindings, holder)`, which looks the binding up **by name**
and throws when there is none. Three call sites collapse into it, and `?? 'p0'` — which drew
two holders with one object — is gone from all of them.

Positioning had the same shape in a different place: vertical-blank setup positioned the first
band's objects at the first band's *scores'* x, `firstScores[i]?.x ?? 0`. It now asks the
holder itself, whether that holder is a score or an actor.

## The band-transition rule was wrong, not just its inputs

`layout` charged a transition only for objects the **previous** band had placed:

> *A boundary costs scanlines only for objects that were already placed somewhere else.*

An object drawn by band N and by no band before it is not free — it is **unplaced**. That is
how P1 ended up at pixel 120 in the one-score scene: it belonged to the field, to no band
before it, and to neither the first band's vertical-blank positioning nor the transition.

Every object a band draws is now placed at its boundary, the first band excepted because
vertical blank places everything there. For `tank-arena` the two rules agree — both bands use
both objects — which is why the ledger is byte-identical and the 90-frame comparison never
moved.

## `within` means something now

It was parsed, checked for existence (E206), passed into lowering, and used **in a comment**.
The bounds came from whichever ledger row carried the note string `'the open field'`.

**E219**: an actor may only be bounded by the band it lives in. A band is a horizontal strip
drawn by its own kernel and an actor is drawn by the kernel of its own band, so clamping tank0
to the HUD's scanlines would confine it to lines nothing draws it on. There is no sensible
picture to emit, so the compiler refuses rather than choosing one.

That also retires the note-string lookup: bounds now come from the ledger row whose **band**
is the actor's, and whose kind is `loop`. A human-readable note is not a key.

## Two more of the same class, found by reading

- **E507, more than one playfield.** `COLUPF` is written once in one-time setup from
  `scene.playfields[0]`, while layout already gives each band its own playfield and decomposes
  them independently. A second one in another colour would draw in the first one's. Refused
  rather than fixed: rendering it properly needs a per-band COLUPF write whose line cost
  nothing has measured, and inventing that cost is the assumed zero the ledger exists to
  prevent.
- **`CTRLPF_MODE` is keyed by the IR's own union** instead of `string`, so the lookup is total
  and the `?? 0` is gone. It mattered: 0 is `repeat`, so a mode the table forgot would have
  rendered un-mirrored rather than failed.

## The selector's decision now reaches the emitter

`emitRowGroup` switched on `ctx.kind` and used its `entry` argument **only inside an error
message**. The catalog's central claim — that the entry decides the code — was true by
coincidence: three entries, one per kind, so switching on the kind and switching on the id
were the same function.

A second `loop` kernel breaks the coincidence, and that is precisely what the next game needs.
It would have been drawn by `emitLoop`, the tank kernel, with a ledger, a budget and a frame
length that all agree with a kernel it is not running.

`EMITTERS` now maps entry id to the emitters it provides per row-group kind. One entry maps to
several kinds, because a field kernel whose `entryLines` is non-zero draws both the priming
line and the loop that follows it.

Two refusals and a guard, all watched failing:

- an entry with no emitter is named, not drawn by kind — `solid-run` asked for a `loop` used to
  return the tank kernel's code quite happily;
- an entry asked for a kind it does not draw says which kinds it does;
- **every kind in a catalog entry's `applies.kinds` must have an emitter.** Two lists naming
  the same entries is the shape that drifts, so adding an entry and forgetting the table is now
  a red test rather than a wrong ROM. Verified by removing `solid-run` from `EMITTERS` and
  watching it go red.

378 tests.

## What Stella showed, and a constant it contradicted

The compiled ROM was opened in Stella to look at the work, and the sprite is exactly what
`tank-arena.p1` declares -- centred two-pixel turret, widening body, the gap between the treads
-- at 262 lines, 60Hz, 4K.

The interesting part was a scene the example does not contain. Building the "no HUD" shape
against `main` and against this branch, side by side:

| | red (tank0, declared x 40) | blue (tank1, declared x 110) |
|---|---|---|
| before this branch | TIA pixel **141** | TIA pixel **3** |
| after | **43** | **113** |

43 and 113 are the declared positions plus the measured `POSITIONING_OFFSET` of 3. The fix is
visible, and it is the only way this branch's work is visible at all -- the committed example
renders identically before and after, which is the point.

**Then Stella contradicted `PLAYER_HBLANK_POSITION = 3`**, one of the constants `objects.ts`
labels UNMEASURED. An object positioned in vertical blank at an authored x of 0 or 1 does not
rest at a minimum; it **wraps to 141**. Agreement is exact at `x + 3` from x = 2 upward.

Checked immediately afterwards, because `movementBounds` gives `xMin = 1`: a full `tank-arena`
with `tank0` declared at 1 renders at pixel 4 in Stella, exactly as the model predicts. The
visible-region transition -- the path every moving actor uses -- is unaffected, so the shipped
game does not teleport a tank when it is driven fully left. The error is confined to vertical
blank, which is a first band holding actors: the scene shape that only began compiling
correctly today.

Recorded in `docs/kernel-measurements.md` under
[An object positioned in vertical blank wraps](../kernel-measurements.md). Not fixed: two data
points both landing on 141 do not determine the wrap's arithmetic, and inventing it is what
the UNMEASURED label exists to prevent.
