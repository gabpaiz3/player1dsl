## Decisions made

| Decision | Rationale |
|---|---|
| Equivalence is the TIA-write trace, not ROM bytes | Byte-identity forbids the compiler from ever choosing a different-but-correct instruction sequence, which defeats the template catalog before it exists. |
| The colour clock is recorded but never asserted | Clock position is a function of instruction cycle counts. Asserting it tests transcription fidelity, not compilation. The register's read deadline is the part that decides what appears on screen. |
| The `.p1` states game-layer intent only | No scanline counts, no timer values, no write ordering. Anything the source states is a claim the compiler never has to earn. |
| Raster kernels templated, VBLANK/overscan logic compiled | The raster tricks are hardware-shaped and measured; the rules are ordinary control flow. Synthesising raster code from a cycle model is the general solver the spec rejects on determinism grounds. |
| General IR, one validated instance | The language must eventually carry paddle games and canyon-runners, so the IR is a bounded expression language with genre vocabulary as intrinsics. Step 3 validates one instance and says so — "a new genre costs a catalog entry, not compiler surgery" is left falsifiable and **untested**. |
| Kernel-shape fixtures before the catalog interface (increment 4b) | The applicability vocabulary is to step 3 what the band model was to step 1. Deriving it from one kernel and validating at step 4 repeats the mistake the roadmap's ordering argument exists to avoid. |
| No third-party game sources | An open-source repo of Combat/Adventure/Pitfall/River Raid disassemblies was considered and rejected: `license: null`, and AGENTS.md forbids third-party ROMs and recovered commercial assets. The specific hazard is that kernel structure copied from one would land in `packages/runtime`, which ships inside every generated ROM. |
| The golden harness before any compiler code | It is the acceptance criterion made runnable. Built last, "equivalent" gets defined during codegen debugging — when the definition is least trustworthy. |

## The line ledger, measured

Step 3's acceptance criterion looked circular. SPEC §4.4 defers the band-transition cost
model *to* step 3, but scanline-exact trace equality requires the compiler to
independently produce `FIELD_LINES = 158`.

It is not circular. Measuring the reference ROM's real region boundaries — not its
comments, three of which are stale and still claim a 176-line field — gives a ledger that
balances on two rules step 1 already measured:

| Row group | Kind | Frame lines | Count | Source |
|---|---|---|---|---|
| HUD band | band | 40–51 | 12 | authored |
| Band transition | transition | 52–56 | 5 | derived: `2n + 1`, `n = 2` |
| Top wall | run | 57–64 | 8 | authored |
| Field setup | setup | 65 | 1 | derived: region change after a loop exit |
| Field loop | loop | 66–223 | **158** | **solved: the remainder** |
| Bottom wall | run | 224–231 | 8 | authored |
| **Visible** | | | **192** | |

The two wall rows are **not** structural. A band is a sequence of `(kernel, line count)`
row groups; `[wall][field][wall]` is what an arena game happens to decompose into, and
most genres have no border at all.

## Findings that contradicted a prediction

### 1. The golden collapsed nothing — 489 KB against a predicted 50 KB

The plan predicted roughly 50 KB. The first generated golden was **489 KB and 33,390
records**, with **zero** runs collapsed in 90 frames.

Cause: run detection merged writes adjacent in the *stream*, but `GRP0` and `GRP1`
alternate on every line of the field loop, so no two consecutive writes ever share a
register and the detector never fired once. The reasoning *"the field loop writes
`GRP0=$00` for most of 158 lines, so it collapses"* was true about the ROM and false
about the algorithm.

Fixed by collapsing per **scanline signature**: merge consecutive lines whose entire write
sequence is identical and all-blank. 489 KB → 115 KB, 33,390 → 6,990 records, 1,316 runs.
The golden is now readable — the tank sprite rows show as `$18`/`$7e`/`$ff` at lines
105–111.

### 2. The movement bounds are asymmetric

Predicted the tank would rest at `X_MIN`. It rests at **7, one past `X_MIN = 8`** — while
the *upper* bound rests at exactly `Y_MAX = 155`.

Cause is the comparison sense. `cpx #X_MIN / bcc` skips the decrement only when the
position is *already* below the bound, so `x = 8` still decrements. `cpx #Y_MAX / bcs`
skips at or above, so `y` stops exactly on 155.

**This is load-bearing for step 3.** `within bounds` in the `.p1` must lower to this exact
asymmetry: a symmetric clamp puts the tank one pixel off, and every later `RESPx`/`HMPx`
write in the trace diverges. Pinned with explicit values in
`tank-arena-behaviour.test.ts`.

### 3. `golden-late` did not isolate the deadline check

The plan's design for known-positive 2 was a mutation invisible to the equality half.
Comparing `golden-late` against `golden-base` turned out to trip the **record** half too:
moving a write from blank into the visible region also changes whether it collapses into a
run.

Added the airtight form — `golden-late` against *its own* trace, where the record half
matches by construction, so any mismatch left can only have come from the deadline check.
Then sabotaged the deadline loop and confirmed exactly those two tests go red. An
assertion nobody has watched fail is not evidence.
