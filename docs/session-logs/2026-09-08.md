# Session log — 2026-09-08

**Branch:** `fix-check-ram`
**Scope:** the one-line defect the 2026-09-07 review found, and the reason it was not one line.

## What happened

`p1 check` reported **10 bytes used and 110 free** where `p1 build` allocated **14**. Four
bytes — two digit pointers per score — invisible in the map the CLI prints and counted as
free space a program could spend.

## The cause was a default, not a typo

`allocateGameRam(game, objects, scores = 0)` had two callers. `build.ts:402` passed
`scene.scores.length`. `cli/src/index.ts:143` passed two arguments and got 0.

Neither call site looks wrong when read on its own. That is what a defaulted parameter buys:
**a missing argument that looks like an answer.** The function's own docblock says it exists
so that `p1 check` and `p1 build` cannot give two answers to "which byte is free" — and the
disagreement arrived through its parameter list instead of through a second allocator.

Same shape as the review's larger finding about `build.ts`: `?? 'p0'`, `?? 0`, `sprites[0]`.
A fallback is a decision made in the absence of information, and it is indistinguishable at
the call site from a decision made with it.

## The fix, in two parts

**`scores` is required.** Omitting it is now a type error. That closes the way this particular
defect arrived, and it is why the change touches `build.ts` at all — the type is the guard.

**A test holds the two together.** `cli.test.ts` runs `p1 check`, computes the allocation the
build makes, and asserts the printed totals match. Deliberately *not* asserting 14 and 110: a
literal would need updating whenever the kernel's scratch changes, and updating a literal to
match new output is how two numbers drift apart while both look maintained. It also asserts
each `digitNPtr` appears by name, because "used" and "free" would still agree with each other
if both were wrong.

**Watched it fail.** With the fix reverted, the test reports
`expected '…' to contain '14 bytes used'` against `10 bytes used, 8 reserved for the stack,
110 free`. The four bytes, exactly as predicted. A test that has never been seen red is a
test nobody has checked measures anything.

## The per-fragment gate, and the fix that was wrong first

`E706`: a rule fragment whose worst-case path exceeds one scanline is now refused.

### What the 2026-09-04 fix actually bought

Ending every rule fragment on `sta WSYNC` was recorded as making its cost "a whole line
whichever way the branch went." That is half true, and the half that is false is the half the
frame driver depends on.

**A WSYNC aligns the END of a fragment to a line boundary. It says nothing about how many
boundaries the code crossed reaching it.** A fragment whose worst path is 84 cycles and whose
best is 30 ends on a boundary either way — after crossing two boundaries on one branch and
one on the other.

### Accounting was tried first, and the ROM refuted it

The first fix charged `ceil(worstCase / 76)` lines instead of one, reasoning that a long rule
simply costs more lines and should still compile. It is the more generous fix, and it is
wrong:

| | Frames observed |
|---|---|
| Before any fix, 3 actions | 262, and **263** on the contact frame |
| Charging 2 lines, 3 actions | 262, and **261** on every frame without contact |

The short branch really does take one line. Charging two makes the frame a line short exactly
where the long branch was not taken — the same input-dependent frame length, mirrored. **A
cost that depends on the input cannot be charged. It can only be refused.**

That is now written where the decision lives, in `ruleLines`, because the refuted approach is
the more instructive half and a reader who reaches for it should find the reason it fails.

### What shipped

- `fragmentCosts` in the runtime: splits emitted text on `sta WSYNC`, costs each fragment on
  its own worst case, and reports trailing cycles as a **remainder** rather than rounding
  them into a line, because they land on a line it cannot see.
- `ruleLines` in the compiler: refuses any fragment over 76 cycles with **E706**, then
  returns the fragment count — which is *provably* the line count once every fragment fits.
- **`MOVE_RULE_LINES` and `COLLISION_RULE_LINES` are gone.** They were a second answer to a
  question the emitted text can now answer, and they were right only while every fragment
  happened to fit.
- Overscan rule cycles stopped being charged against **vertical blank's** budget, and rule
  lines stopped being subtracted from `available` while their cycles were also counted in
  `spent` — E704 was reporting a smaller overrun than the real one.
- `frame.ts`'s "every scanline below is one `sta WSYNC` that provably executed" is true now,
  and says which gate makes it true. It was false in exactly the way above.
- SPEC §13 gains `E706`.

**E706 was watched failing**, on three and four actions, asserted by code and by the cycle
count it reports. It is the first gate in the `E70x` range anything has been seen to trip.

### Still not fired: E704

E705 reaches every over-large scene first, because a fragment costs at least a line and lines
run out before cycles do. E704 stays because it is true — rules cannot spend more cycles than
the region holds, and it covers the un-lined code the line count cannot see — but by this
project's own rule it is not yet a gate. Written down in `checkBudget` rather than left to be
discovered.
