## Two corrections to the approved design, both applied to the design document

### 1. The field-setup line is a template entry cost, not a region-change rule

The design said *"a region change immediately following a loop exit costs one line, because
the loop falls through mid-line and leaves no horizontal blank."*

The reference ROM contains **two** such boundaries and they cost **1 and 0**:

| Boundary | Predicted | Measured |
|---|---|---|
| top wall → field loop | 1 | **1** |
| field loop → bottom wall | 1 | **0** |

The general rule predicts 1 for both, so it is dead. The discriminator is **where a loop
writes its per-line registers**: a loop writing them after each WSYNC cannot render its
first line from data that does not exist yet, so it charges one entry line; a loop whose
registers are set once before it runs is valid from that same line and charges none.

The arithmetic is unchanged. The number moved from compiler-derived to
template-declared — which is where the runtime/compiler split says a measured number
belongs. The `CostModel` abstraction the plan was going to need did not survive: what is
left of "cost rules the compiler applies" is a single integer, *n*.

### 2. The colour clock is asserted for beam-position-sensitive strobes

[Review 0.2 §1.1](../spec-review-0.2.md) is right that a blanket "record the clock, never
assert it" is unsound. `RESP0` takes effect from wherever the beam is, so a ROM can match
`(line, register, value)` and its deadline while drawing the tank somewhere else.

Three timing classes, not the review's two: `exact` (the RESPx strobes), `blank` (`HMOVE`,
`RSYNC`), `deadline` (everything else). Implemented in increment 5, task 13.

`exact` is a **conservative over-constraint, knowingly**: final position is
`(coarse clock, HMPx fine value)`, so a different pair encodes the same *x* and asserting
the clock rejects those alternative encodings. No false negatives, some false positives on
legal-but-different positioning.

Which registers are beam-sensitive is a **hardware fact**, so the table lives in the
emulator beside `FIRST_READ_PIXEL`. Templates declare what they believe, and a test asserts
the two agree — the "second, disconnected rule table" the review warns about is made a test
failure rather than avoided by convention.

## Findings that contradicted a prediction

### An 8-entry sprite table renders 7 lines

The obvious answer was 8 — one line per table entry — and it is wrong. The loop primes one
line ahead, so its final write lands in the *next* line's horizontal blank and is
overwritten there before it can render.

This is the most useful result in the increment: the corrected entry-cost rule has now been
measured on **PF1/PF2** (`scroll-field`), on **GRP0** (`sprite-formation`), and on
**GRP0/GRP1** (tank-arena's own field kernel). One observation became a rule.

The measurement takes the **last** write to a register on each line rather than counting
writes, so the overwritten line falls out of the arithmetic instead of needing a special
case. Counting writes gives 8 and would have been wrong in a way that looked right.

### The obvious way to measure a band boundary is off by one

The first extraction for `ball-and-paddles` was min..max over the `RESP0`/`RESP1`/`RESBL`/
`HMOVE` writes in the visible region. **That gives 6, not 7.** Each `PosObjectX` call is
`WSYNC / … / RESPx / WSYNC / HMOVE`, so the *first* of its two lines carries no traced write
at all — the missing line is at the **front**, where nothing looks for it.

Six would have read as falsifying `2n + 1`. What was wrong was the extraction, and the same
error gives 4 instead of 5 on tank-arena, so it would have looked **consistent** — which is
worse than looking wrong. The boundary is measured instead as the gap between bands, and the
wrong extraction is now itself an assertion so nobody reintroduces it believing it agrees.
